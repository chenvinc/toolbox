## 一、方案层面的补充（影响正确性）

### 1. R-5 的异常兜底只覆盖了一半

`sys.excepthook` 只能捕获**主线程**未处理异常。但项目的耗时操作跑在 `QThread`（`QtTaskRunner`）中：

| 异常来源 | `sys.excepthook` 能否捕获 | 说明 |
|----------|--------------------------|------|
| 主线程（UI 事件处理） | ✅ | 正常覆盖 |
| `QThread.run()` 内 Python 异常 | ❌ | 被 Qt 事件循环吞掉，或仅打印到 stderr |
| Qt C++ 层 `qWarning`/`qCritical` | ❌ | 需要 `qInstallMessageHandler` |
| 原生崩溃（segfault） | ❌ | 需要 `faulthandler` 或外部 watchdog |

**建议补充**：

```python
# 1) QThread 异常兜底：在 QtTaskRunner.run() 最外层
try:
    super().run()
except Exception:
    logger.exception("QThread 未捕获异常")
    # 可选：通过信号通知主线程弹 ErrorDialog

# 2) Qt 内部消息转发到 logging
from PySide6.QtCore import qInstallMessageHandler, QtMsgType
def _qt_msg_handler(mode, ctx, msg):
    level = {QtMsgType.QtWarningMsg: logging.WARNING,
             QtMsgType.QtCriticalMsg: logging.ERROR}.get(mode, logging.DEBUG)
    logging.getLogger("qt").log(level, "%s (%s:%d)", msg, ctx.file, ctx.line)
qInstallMessageHandler(_qt_msg_handler)

# 3) 原生崩溃最低限度留痕
import faulthandler
faulthandler.enable(file=open(log_dir / "crash.log", "w"))
```

不做这三步，R-5 的"可追溯性"在后台线程场景下仍然是空话。

### 2. R-3 的 lambda 存在生命周期风险

```python
self._spin.valueChanged.connect(lambda v: self.valueChanged.emit(float(v)))
```

- lambda 隐式捕获 `self`（`StepperInput` 实例）。如果 `StepperInput` 被从布局中移除但未被 `deleteLater()`，而内部 `_spin` 仍存活（如被其他地方引用），信号触发时会访问已半销毁的对象。
- PySide6 中 lambda 连接**不会**随 `self` 销毁自动断开（与 `self` 作为 receiver 的槽不同）。

**建议**：

```python
# 方案 A：用 self 作为 context（PySide6 6.x 支持）
self._spin.valueChanged.connect(self._relay_value, self)

def _relay_value(self, v):
    self.valueChanged.emit(float(v))

# 方案 B：显式在 closeEvent / deleteLater 前 disconnect
```

另外，`QDoubleSpinBox.valueChanged` 本身已发射 `float`，`float(v)` 对其是冗余的（无害但多余）；只有 `QSpinBox` 路径需要 `int → float` 转换。建议按类型分两个连接，语义更清晰。

### 3. R-1 的 `changeEvent` 方案有一个边界需明确

当外部直接调 `setEnabled(False)`（不经过 `set_actionable`）时：

- `changeEvent` 触发 → `_can_click = False` → **不清空 reason**
- 如果上一次 `set_actionable(False, "请先选择文件")` 留了 reason，此时 reason 仍为 `"请先选择文件"`

这个行为**可能是对的**（保留上下文），也可能是**意外残留**。建议在代码注释或文档中明确声明设计意图：

> `setEnabled(False)` 不修改 reason；reason 的生命周期完全由 `set_actionable` 管理。

否则后续维护者会困惑"为什么 setEnabled(False) 之后 tooltip 还显示旧 reason"。

## 二、范围层面的补充（影响完整性）

### 4. R-4 的加固范围需要全仓扫描

文档只提到了 `float(settings.value(...))` 这一处。但 QSettings 的脏值风险是**系统性的**：

- `int(settings.value(...))` — 同理
- `settings.value(key, defaultValue, type=bool)` — PySide6 的 type 参数在某些版本下不生效
- `restoreGeometry(settings.value("geometry"))` — 脏值导致窗口不可见
- `restoreState(settings.value("windowState"))` — 同上

**建议**：在 R-4 执行前，先跑一次全仓 grep：

```bash
grep -rn "settings\.value\|\.restoreGeometry\|\.restoreState" ui/
```

列出完整清单，逐一加固。否则修了 `float()` 那处，`restoreGeometry` 那处照样崩。

### 5. R-6 的元测试需要解决"如何发现所有子类"的问题

```python
def test_every_view_registered_in_app():
    """BaseView 子类必须出现在 ToolboxApp._register_tools"""
```

问题：
- `BaseView.__subclasses__()` 只能发现**已被 import** 的子类。如果测试没有 import 所有 view 模块，就会漏检。
- 但 import view 模块可能触发 `QApplication` 创建（如果模块顶层有控件实例化）。

**建议**：
- 在测试中显式 `import ui.views`（确保 `__init__.py` 导出所有 view），或
- 用 `pkgutil.walk_packages` 扫描 `ui/views/` 下所有模块并动态 import，或
- 更简单：在 `ui/views/__init__.py` 中维护一个 `ALL_VIEWS: list[type[BaseView]]` 注册表，测试直接断言这个列表与 `app.py` 的注册一致。

同理，`test_eventtypes_are_partitioned_across_viewmodels` 需要确认 `_WATCHED` 是**类属性**（可在不实例化的情况下读取）。如果是实例属性，测试就需要构造 VM——而 VM 构造可能依赖 container。

### 8. 缺少回滚策略

P0 的 5 个修复合入后，如果 R-1 的 `changeEvent` 方案在某些 Qt 版本下行为不一致（如 PySide6 6.5 vs 6.7 的 `changeEvent` 触发时机），如何快速回滚？

**建议**：
- P0 的 5 个修复各自独立 commit，不合并为一个 PR
- R-8/R-9 在独立分支上进行，合入前必须 `110 passed` 全绿
- 明确"止损点"：如果 R-9 改到一半发现 4 个 View 的差异无法用参数化收敛，允许回退到"只上提滚动条样式"的最小方案

### 9. R-9 需要先做差异分析再动手

文档说"将 `_make_module_card`、`_make_labeled_field` 上提至 `BaseView`"，但 4 份实现是否**逐字相同**？

- 如果卡片内控件数量不同（如 A 工具 3 个按钮，B 工具 5 个），上提后方法签名会膨胀
- 如果布局方向不同（水平 vs 垂直），参数化会让基类方法变得难以理解

**建议**：R-9 的第一步不是写代码，而是：

```bash
# 提取 4 份实现做 diff
grep -A 30 "_make_module_card" ui/views/*.py > /tmp/cards.txt
diff ...
```

确认差异点后，决定是"上提 + 参数"还是"上提骨架 + 子类实现 `_build_card_content()`"。

## 四、决策层面的补充

### 10. P2 缺少时间触发器

> "随下一个新工具落地时一并做"

如果下一个新工具 6 个月后才来，R-10/R-11/R-12 就无限期搁置。建议改为：

> 随下一个新工具落地时一并做；**若 3 个月内无新工具需求，则在第 4 个月初单独安排一个迭代完成。**

---

### 11. N-01/N-02 缺少根因分析

发现了问题、给出了修复，但没有回答"**为什么会出现**"：

- **N-01**（`_apply_global_font` 藏了 86 行装配逻辑）：大概率是早期原型阶段"先跑起来再说"，后来不断往里加东西，方法名没跟着改。根因是**缺少"方法职责单一"的 code review 检查点**。
- **N-02**（QSettings 脏值崩溃）：大概率是早期只有开发者自己用，不会写脏值；上线后用户环境不可控。根因是**缺少"外部输入不可信"的防御性编程规范**。

补充根因分析的价值在于：防止同类问题在其他地方再次出现。建议在整改完成后，将这两条根因写入开发指南的"避坑清单"。

---

### 12. 建议不采纳的 W-04 可以更进一步

文档将 W-04 降为 P3 可选，理由是 `files_selected([])` 已可观测。这个判断是对的。但可以补充一句：

> 若未来 `MultiDropZone` 需要区分"用户主动清空"和"程序调用 `clear_all()`"，则 `file_cleared` 信号仍有必要。当前不需要，但应在 `MultiDropZone` 的 docstring 中注明"清空事件通过 `files_selected([])` 表达"，避免后续开发者误以为缺失。
