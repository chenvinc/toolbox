### 0.1 需要向评审方指出的四点偏差

**① A-05「无 logging」不成立 —— 这是最需要纠正的一条。**
项目已有完整 logging 接线：`app.py` 配置 `basicConfig`，4 个 View + `open_folder.py` + `_exam_image_fetch.py` 均有 `logger = getLogger(__name__)` 并实际调用 `logger.info/error`，且 `tests/test_p2_tech_debt.py` 有护栏测试禁止 `print(` 残留。
真正缺失的是：**无文件 Handler**（打包为 GUI 后 stderr 丢失，等于没有日志）、**无 `sys.excepthook`**（UI 线程未捕获异常静默崩溃）、**core 层日志稀疏**、无崩溃上报。结论应从「缺乏可观测性」修正为「日志已接线但不可留存」，整改成本因此从「高」降为「低」。

**② 评审引用的文件路径是过时的。**
评审中的 `services/extraction.py`、`viewmodels/extraction.py`、`viewmodels/slide.py`、`PdfOutlineService` 在当前代码库中**均不存在**，实际为 `core/services/json_to_word_service.py`、`ui/viewmodels/json_exam_viewmodel.py`、`ui/viewmodels/slide_viewmodel.py`、`PdfSlideServiceImpl`。说明评审主要依据 `architecture.md` 等文档撰写，未完全对照当前代码。这不影响结论有效性，但 D-09 的类名是错的（`PdfSlideServiceImpl` 已正确导出）。

**③ 汇总统计有算术错误与重复计数。**
- 🟢 实际为 **13** 项（D-01~D-09 共 9 + M-01/02/03/06 共 4），非 14；🔴 实际为 **18** 项，非 17。
- **D-11 与 W-01 是同一个缺陷**（`AppButton.setEnabled` 重写），被计了两次。故 36 条实际描述 **35 个不同问题**。

**④ W-04 影响被高估。**
`MultiDropZone` 确实没有 `file_cleared` 信号，但 `clear_all()` 会发射 `files_selected([])`，**清空事件完全可观测**。这是与 `DropZone` 的 API 不对称，不是「功能缺失」。严重度应从「缺陷」降为「一致性优化」。

### 0.2 评审未发现的两个问题（本次核实新增）

**N-01｜`app.py` 的 `_apply_global_font()` 名不副实（比 A-06 更具体、更严重）**
该方法名为「应用全局字体」，实际却包含：窗口标题/尺寸设定、**完整 DI 装配**、4 个 ViewModel 构造、侧边栏与 StackedWidget 布局搭建、工具注册、主题接线。而 `__init__` 本身只有 3 行。
即整个应用的构造逻辑被藏在一个字体方法里（`app.py:46-131`，共 86 行）。这是 A-06「职责过重」的具体病灶，任何人接手都会被误导。

**N-02｜QSettings 脏值会导致应用启动崩溃（已复现）**
`ui/views/similarity_view.py:478` 与 `:661` 直接 `float(self.settings.value(SimilarityKeys.THRESHOLD, 0.8))`，无异常保护。若持久化值被写脏（崩溃、手改、跨版本格式变更），View 构造即抛 `ValueError`，**应用无法启动且用户无自救途径**。
这比 A-12 泛泛的「可能留下脏状态」具体得多，且严重度应为「高」而非「低」。

复现证据：

## 3. 整改计划

优先级依据「**风险 × 修复成本**」重排，与评审建议的顺序有意不同：评审把 A-05 排第一，但核实后 A-05 成本极低；而被评为「低」的 A-12 实际可导致启动崩溃，应前置。

### P0 — 立即修复（1 个工作日内，全部为小改动高收益）

**R-1｜修复 `AppButton.setEnabled` 契约违反（W-01 / D-11）**
不再重写 `setEnabled`，改用 Qt 正统的 `changeEvent` 钩子同步视觉状态：

```python
from PySide6.QtCore import QEvent

def set_actionable(self, actionable, reason=""):
    self._disabled_reason = reason          # 先置 reason
    super().setEnabled(actionable)          # 触发 changeEvent 同步样式/光标

def changeEvent(self, event):
    if event.type() == QEvent.EnabledChange:
        self._can_click = self.isEnabled()
        if self._can_click:
            self._disabled_reason = ""      # 仅启用时清空，语义正确
        self._update_cursor()
        self.update_style()
    super().changeEvent(event)
# 删除现有 setEnabled 重写
```
效果：`setEnabled(False)` 不再吞掉 reason；Qt 原生语义恢复；样式仍自动同步。

**R-2｜修复 `DropZone`/`MultiDropZone` 的 `theme=None`（W-03）**
与 `AppButton`/`StepperInput` 已有写法保持一致，各改一行：
```python
self._theme = theme if theme is not None else Theme()
```
随后可清理 `_apply_style()` 中已失效的 `if t else` 半吊子兜底。

**R-3｜修复 `StepperInput.valueChanged`（W-02）**
在 `__init__` 中桥接内部控件信号，一次性覆盖「按钮点击」与「直接输入」两条路径：
```python
if isinstance(self._spin, (QDoubleSpinBox, QSpinBox)):
    self._spin.valueChanged.connect(lambda v: self.valueChanged.emit(float(v)))
```
配套：将 `similarity_view.py:510` 改为连接 `self._threshold_stepper.valueChanged`，消除封装泄漏。

**R-4｜QSettings 读取加固（N-02 / A-12）**
新增 `ui/infra/settings_keys.py` 同级的安全读取助手，全部 `settings.value()` 调用点改用：
```python
def read_float(settings, key, default): ...   # try/except ValueError/TypeError → default
def read_bool(settings, key, default): ...
def read_str(settings, key, default): ...
```
彻底消除「脏配置导致应用打不开」的死锁场景。

**R-5｜日志落盘 + 全局异常兜底（A-05，成本远低于评审估计）**
`app.py` 中替换现有 `basicConfig`：
```python
log_dir = Path(QStandardPaths.writableLocation(QStandardPaths.AppDataLocation)) / "logs"
log_dir.mkdir(parents=True, exist_ok=True)
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(name)s: %(message)s",
    handlers=[
        RotatingFileHandler(log_dir / "toolbox.log", maxBytes=2*1024*1024,
                            backupCount=3, encoding="utf-8"),
        logging.StreamHandler(),
    ],
)
sys.excepthook = lambda t, v, tb: logging.getLogger("unhandled").critical(
    "未捕获异常", exc_info=(t, v, tb))
```
并补齐 `core/services/` 各服务入口的 INFO 级日志。**崩溃上报（Sentry 等）单列，非本期范围。**

## 6. 第二轮评审意见核实与采纳（2026-08-02）

第三方专家针对本文档提出 12 条补充意见（见 `docs/第三方评审对核实与整改方案的第二轮意见建议.md`）。
